# ADR-001: API Gateway и Аутентификация

## Статус
Accepted

## Контекст
В текущей архитектуре nginx выступает простым reverse proxy: SPA → `/`, API → `backend:8081`.
Аутентификация есть только на публичном API (`/api/v1/*` через SHA256 Bearer token).

При переходе к микросервисам нужно:
- Единая точка входа для фронтенда
- Маршрутизация запросов к правильному сервису
- Аутентификация и rate limiting
- Проброс WebSocket-соединений
- TLS-терминация

## Решение
Используем **nginx** как API Gateway.

### Почему nginx
- Уже используется в текущей архитектуре — migration path без новых зависимостей
- Максимальная производительность при минимальных ресурсах
- Встроенный rate limiting, WebSocket proxy, заглушки для статики
- Конфигурация в YAML, легко читается и версионируется
- Для single-user системы не нужен Kong/Ambassador/Traefik

### Аутентификация

**Внутренние запросы (localhost / Docker network)**
- Без аутентификации
- Только для запросов от API Gateway к сервисам
- Все сервисы слушают localhost / internal Docker network

**Публичные запросы (`/api/v1/*`)**
- Bearer token в заголовке `Authorization: Bearer psk-...`
- SHA256 хэш токена сверяется с `integrations_/api_keys`
- Rate limit: 100 req/min per key (nginx `limit_req_zone`)

**WebSocket**
- Аутентификация через query param при подключении: `wss://host/ws?token=psk-...`
- Gateway проверяет токен, при невалидном — закрывает соединение

### Rate Limiting

```nginx
limit_req_zone $binary_remote_addr zone=internal:10m rate=100r/s;
limit_req_zone $http_authorization zone=public:10m rate=100r/m;

server {
    location /api/ {
        limit_req zone=internal burst=200 nodelay;
        proxy_pass http://service_upstream;
    }
    location /api/v1/ {
        limit_req zone=public burst=20 nodelay;
        # + API key validation
    }
}
```

### TLS

- В dev-среде: без TLS (localhost)
- В production: внешний reverse proxy (Caddy / Cloudflare Tunnel / nginx с certbot)
- Сервисы внутри Docker сети всегда по HTTP

### Кеширование

```nginx
# index.html — никогда не кешируется
location = /index.html {
    add_header Cache-Control "no-cache, no-store, must-revalidate";
}

# hashed assets — кеш навсегда
location ~* \.(js|css|svg|woff2?)$ {
    add_header Cache-Control "public, immutable, max-age=31536000";
}
```

### Health Check

```nginx
location /api/health {
    return 200 '{"ok":true}';
    add_header Content-Type application/json;
}
```

## Последствия

### Положительные
- Единая точка входа и конфигурации маршрутизации
- Изоляция сервисов: ни один сервис не доступен напрямую извне
- Знакомый стек (уже используется в nginx)
- Аутентификация и rate limit в одном месте, не в каждом сервисе

### Отрицательные
- Каждый новый сервис требует изменения nginx.conf
- Нет service discovery — маршруты статические (достаточно для single-machine)
- nginx не умеет агрегировать ответы от нескольких сервисов (graphql / bff понадобится отдельно)
