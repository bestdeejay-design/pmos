# ADR-002: Testing and Quality Strategy (Тестирование и Качество)

## Статус
Accepted

## Контекст
В текущем монолите тесты отсутствуют полностью. Нет ни unit-тестов, ни интеграционных, ни E2E.
Каждое изменение делается «на глаз» и проверяется вручную в браузере. Это привело к:
- Регрессиям при каждом втором изменении
- Невозможности рефакторить с уверенностью
- «Странно у тебя работает диктофон» — баги, которые могли быть отловлены тестами

При переходе к микросервисам тестирование становится критичным: сервисы должны соблюдать контракты,
события не должны теряться, API не должно ломаться при изменениях.

## Решение
Внедряем многоуровневую стратегию тестирования (Test Pyramid для микросервисов).

### Уровни тестирования

```
         ╱╲
        ╱ E2E ╲           ← Playwright: полный сценарий (3-5 тестов)
       ╱────────╲
      ╱ Contract ╲        ← Pact: межсервисные контракты (10-20 тестов)
     ╱────────────╲
    ╱ Integration  ╲      ← docker-compose: потоки событий (20-40 тестов)
   ╱────────────────╲
  ╱   Unit Tests      ╲   ← vitest: каждая функция (100-300 тестов)
 ╱──────────────────────╲
```

### 1. Unit Tests (vitest)

- **Что тестируем**: бизнес-логику сервисов (recurrence expansion, streak calculation, priority ranking, conflict detection, event handlers, validation)
- **Как**: mock event bus, mock DB (in-memory SQLite или тестовая БД)
- **Покрытие**: >80% для критической логики
- **Конвенция**: файлы `*.service.test.ts`, co-located с исходником
- **Команда**: `cd services/notes && npx vitest run`

**Примеры тестов**:
- notes: создание, обновление, удаление заметки, AI-генерация заголовка (timeout)
- tasks: рекурренс создаёт новую задачу после закрытия, streaks увеличиваются, зависимости блокируют закрытие
- calendar: рекурренс разворачивает события, конфликты обнаруживаются
- ai-gateway: fallback chain при недоступности первой модели
- agent: триггеры срабатывают по расписанию

### 2. Integration Tests

- **Что тестируем**: Event flow между 2-3 сервисами
- **Как**: `docker compose` с реальными NATS + PostgreSQL + тестируемыми сервисами
- **Покрытие**: все основные event chains

**Примеры сценариев**:
1. Создать заметку → проверить что search-rag получил `notes.created` и сохранил embedding
2. Создать задачу с рекурренсом → закрыть → проверить что создалась новая
3. Изменить профиль → проверить что подписанные сервисы обновили кэш

### 3. Contract Tests (Pact)

- **Что тестируем**: API-контракты между сервисами
- **Как**: Pact framework. Провайдер публикует контракт, потребитель проверяет
- **Покрытие**: все эндпоинты api-gateway, все типы событий

**Consumer-Driven Contracts**:
```
profile-service (provider) → Pact file → notes-service (consumer) проверяет
notes-service (provider) → Pact file → search-rag (consumer) проверяет
```

Каждый сервис публикует:
- OpenAPI spec для своих HTTP-эндпоинтов
- Event schemas для событий, которые он шлёт
- Event schemas для событий, на которые подписан

### 4. E2E Tests (Playwright)

- **Что тестируем**: Полный пользовательский сценарий через браузер
- **Как**: Playwright, headless Chromium, подключение к dev-стенду
- **Покрытие**: 3-5 критических сценария (CRUD заметки, создание задачи с рекурренсом, поиск)

**Пример сценария**:
```
1. Открыть localhost:8080
2. Создать заметку "купить молоко"
3. Переключиться на поиск
4. Ввести "молоко"
5. Увидеть заметку в результатах
```

### Quality Gates (CI/CD)

```yaml
# .github/workflows/ci.yml — каждый push в main / PR
steps:
  - lint:     eslint + prettier --check          # 30s
  - types:    tsc --noEmit                        # 1min
  - unit:     vitest run                          # 2min
  - build:    npm run build                        # 2min
  - contract: pact verify                         # 3min
  - integration: docker compose up --wait && npm run test:integration  # 5min
  - e2e:      npx playwright test                  # 3min
```

**Fail fast**: lint/typing не прошли → остальные шаги не запускаются.

### Регрессионная политика

1. Каждый баг-фикс включает тест, который ловит этот баг
2. Если тест написать невозможно (UI-специфичный баг) — описание сценария воспроизведения в issue
3. Нулевая толерантность к `as any`, `@ts-ignore`, `@ts-expect-error` — CI это проверяет
4. Mutation testing для критических путей (опционально, `stryker`)

### Pre-commit хуки

```bash
# .husky/pre-commit
npx lint-staged              # eslint + prettier
npm run typecheck            # tsc --noEmit
npx vitest related --run     # тесты, связанные с изменёнными файлами
```

### Инструментарий

| Инструмент | Назначение | Почему |
|-----------|-----------|--------|
| vitest | Unit + integration tests | Быстрый, совместим с Vite, esbuild-based |
| Pact | Contract tests | Стандарт де-факто для CDC в JS/TS |
| Playwright | E2E tests | Единственный серьёзный выбор для современных браузеров |
| ESLint + Prettier | Code quality | Стандарт, настраиваем под strict |
| Husky + lint-staged | Pre-commit | Минимум оверхеда |
| @tsconfig/strict | TypeScript strict | Базовая защита |

### Сервис-специфичные требования

| Сервис | Приоритет тестов | Критические тесты |
|--------|-----------------|-------------------|
| notes | Unit > Contract | Создание/удаление заметки, генерация заголовка |
| tasks | Unit > Contract | Рекурренс, streaks, зависимости, ранг |
| calendar | Unit > Contract | Рекурренс, конфликты, ICS генерация |
| search-rag | Integration > Unit | Event handler → embedding → поиск |
| ai-gateway | Integration > Unit | Fallback chain, timeout |
| agent | Integration > Contract | Триггеры, цепочка: событие → сообщение |
| email | Integration > Unit | IMAP sync, конвертация в note/task |
| профили | Contract > Unit | CRUD |
| settings | Contract > Unit | KV upsert |

## Последствия

### Положительные
- Каждый баг можно отловить тестом до деплоя
- Контрактные тесты не дают сервисам «молча сломать» друг друга
- Рефакторинг с уверенностью: тесты докажут что поведение не изменилось
- Быстрая обратная связь: CI за 5-10 минут

### Отрицательные
- Нужно написать ~200 тестов на старте (инвестиция 1-2 недели)
- Pact требует инфраструктуры (Pact Broker) для хранения контрактов
- Integration тесты медленнее (docker compose поднимается ~30-60s)
