# ADR-003: Event-Driven Communication (Event Bus)

## Статус
Accepted

## Контекст
В текущем монолите вся коммуникация — прямые вызовы функций в рамках одного процесса.
Межсервисного взаимодействия нет. WebSocket-пуши идут напрямую из backend во фронтенд,
background-воркеры живут в том же процессе.

При переходе к микросервисной архитектуре сервисам нужно:
- Уведомлять друг друга об изменениях данных
- Строить собственные read model'и на основе чужих данных
- Поддерживать асинхронные рабочие процессы (создание заметки → AI-генерация заголовка)
- Обеспечить слабую связанность

## Решение
Используем **NATS с JetStream** как единую шину событий.

### Почему NATS
1. **Один бинарник, запуск в 1 секунду** — идеально для `docker compose up`
2. **NATS JetStream** — at-least-once доставка, persistence на диск
3. **Нативная поддержка TypeScript** через официальный `nats.ts` клиент
4. **Request-Reply паттерн** встроен
5. **Не требует кластеризации** — standalone mode для single-machine
6. **Alpine-образ 15MB**, практически ноль CPU/RAM

### Формат события

```typescript
interface Event {
  id: string;                    // UUID v4
  type: string;                  // "notes.created" | "tasks.updated"
  source: string;                // имя сервиса-отправителя
  timestamp: string;             // ISO 8601
  data: Record<string, unknown>; // тело события
  correlationId: string;         // для трейсинга цепочек
  version: number;               // версия схемы события
}
```

### Event Catalog

#### Core events
- `profiles.created/updated/deleted` — profiles → notes, tasks, calendar, search-rag, agent
- `settings.changed` — settings → api-gateway (перезагрузка)

#### Notes events
- `notes.created/updated/deleted` — notes → search-rag, agent, export-import, sync, integrations
- `notes.title_generated` — notes (через ai-gateway) → api-gateway (WS клиенту)

#### Tasks events
- `tasks.created/updated/deleted` — tasks → search-rag, agent, projects, time-tracking, integrations
- `tasks.status_changed` — tasks → agent (deadline_soon trigger)
- `tasks.priorities_reordered` — tasks → (только клиенту через WS)

#### Calendar events
- `meetings.created/updated/deleted` — calendar → search-rag, agent, projects, integrations
- `meetings.reminder` — calendar → api-gateway (WS push)

#### Projects / Files events
- `projects.created/updated/deleted` — projects → agent, integrations
- `files.uploaded/updated/deleted/text_extracted` — files → search-rag

#### AI / Agent events
- `dictation.completed` — ai-gateway → agent (лог), api-gateway (WS)
- `agent.message_created` — agent → api-gateway (WS push), integrations (webhook)
- `agent.trigger_evaluated` — agent → (лог)

### Гарантии доставки
- **At-least-once** через NATS JetStream consumer ack
- **Dead letter** — после 3 неудач сообщение в `{subject}.dlq`
- **Идемпотентность** — подписчик проверяет `event.id` в своей БД

### Saga Pattern
Choreography-based saga. Пример: создание заметки + AI-генерация заголовка.
1. notes публикует `notes.created`
2. ai-gateway генерирует заголовок, публикует `notes.title_generated`
3. notes обновляет запись, публикует `notes.updated`
При таймауте ai-gateway — notes продолжает с заголовком по умолчанию.

## Последствия
- Слабая связанность сервисов
- Eventual consistency (секundy задержки в read model'ях)
- Сложнее отладка (correlationId обязателен)
- Дополнительный сервис (NATS) в стеке
