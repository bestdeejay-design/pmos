# ADR-004: Database per Service (Изоляция данных)

## Статус
Accepted

## Контекст
В текущем монолите все 22 таблицы в одной PostgreSQL базе с FK-связями между доменами.
При переходе к микросервисам общая БД создаёт проблемы: случайные изменения чужих таблиц,
конфликты миграций, невозможность независимого масштабирования.

## Решение
**Одна БД, отдельная схема PostgreSQL на сервис.**

### Почему не отдельные БД
- Для single-user системы 15+ контейнеров PostgreSQL — оверхед без смысла
- Бэкапить одну БД проще
- При необходимости каждая схема выносится в отдельную БД без изменения кода

### Правила
1. **Схема = имя сервиса**: `notes_`, `tasks_`, `calendar_`, etc.
2. **Нет FK между схемами** — только UUID-ссылки, целостность в коде
3. **Миграции** — `services/<name>/migrations/YYYYMMDDHHMMSS_desc.sql`
4. **Каждый сервис** — `SET search_path TO <service_name>`
5. **Read model'и** строятся из событий, прямыми запросами к чужим схемам — нельзя

### Схема данных

| Схема | Таблицы |
|-------|---------|
| `profiles_` | profiles |
| `settings_` | settings |
| `notes_` | notes, templates, note_links |
| `tasks_` | tasks, task_dependencies |
| `calendar_` | meetings, reminders |
| `projects_` | projects |
| `files_` | file_meta |
| `search_rag_` | embeddings (pgvector) |
| `ai_gateway_` | ai_log |
| `agent_` | agent_messages, agent_runs |
| `email_` | imap_accounts, emails |
| `external_calendars_` | external_calendars, external_events |
| `time_tracking_` | timesheet, pomodoro_sessions |
| `integrations_` | api_keys, webhooks, webhook_deliveries |
| `sync_` | sync_folders |
| `export_import_` | export_jobs |

### Shared Kernel
- `profiles_/profiles` — read-only для всех (кэш через события)
- `settings_/settings` — read-only для всех (кэш через `settings.changed`)

### Read Model'и из событий
- search-rag: `notes.created` → embedding → `search_rag_.embeddings`
- agent: `meetings.created` → read model встреч на сегодня
- projects: `notes.*`, `tasks.*` → актуализация items dashboard

## Последствия
- Полная изоляция данных
- Независимые миграции
- Возможность вынести любой сервис в отдельную БД
- Нет FK-проверок между сервисами (контроль в коде)
- Read model'и могут отставать на ~0.5-2s
