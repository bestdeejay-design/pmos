# ADR-005: Observability (Логи, Метрики, Трассировка)

## Статус
Accepted

## Контекст
Текущий монолит не имеет централизованного логирования, метрик или трассировки.
Ошибки читаются из `console.log` в stdout Docker-контейнера. При переходе к микросервисам
такой подход сделает отладку невозможной: запрос проходит через api-gateway → сервис →
шину событий → другой сервис, и без observability нельзя понять, где упало.

Для single-user системы не нужен enterprise-стек (OpenTelemetry + Jaeger + Grafana),
но нужен прагматичный минимум: структурированные логи + базовые метрики.

## Решение

### 1. Структурированные логи (JSON)

Каждый сервис пишет логи в stdout в формате JSON. Docker Compose собирает весь stdout
в один поток, при необходимости можно фильтровать по `service`.

```typescript
// Пример строки лога
{
  "level": "info",
  "service": "notes",
  "correlationId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "msg": "note created",
  "noteId": "uuid-of-new-note",
  "durationMs": 42,
  "timestamp": "2026-07-30T14:00:00.000Z"
}
```

**Уровни логирования**:
- `error` — пользователь видит ошибку, надо разбираться
- `warn` — что-то неожиданное, но не критическое (Ollama недоступен, пал fallback)
- `info` — ключевые действия (создана сущность, опубликовано событие)
- `debug` — подробности для отладки (вход/выход из функции, тело запроса)

**Библиотека**: `pino` — самая быстрая, JSON по умолчанию, `pino-pretty` для dev.

**Что логировать**:
- Входящие HTTP-запросы (method, path, status, durationMs)
- Исходящие события (event type, id, correlationId)
- Полученные события (event type, обработка успех/ошибка)
- Ошибки БД, ответы сторонних API
- **Не логировать**: пароли, тела запросов с контентом пользователя (кроме debug)

### 2. Метрики (prom-client)

Каждый сервис экспонирует эндпоинт `GET /metrics` для Prometheus.

**Стандартные метрики**:
- `http_requests_total` — счётчик запросов по методу, пути, статусу
- `http_request_duration_ms` — гистограмма длительности запросов
- `events_published_total` — счётчик опубликованных событий по типу
- `events_processed_total` — счётчик обработанных событий по типу (с тегом success/failure)
- `db_query_duration_ms` — гистограмма запросов к БД
- `service_info` — gauge с версией сервиса (1 = запущен)

**Библиотека**: `prom-client` (официальный клиент Prometheus для Node.js).

**В docker-compose**:
```yaml
services:
  prometheus:
    image: prom/prometheus
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml
    ports:
      - "9090:9090"

  grafana:
    image: grafana/grafana
    ports:
      - "3000:3000"
    depends_on:
      - prometheus
```

**Примечание**: Prometheus + Grafana запускаются только при необходимости.
По умолчанию — только `/metrics` эндпоинт, данные можно смотреть через `curl`.
Для single-user системы дашборды в Grafana — nice-to-have, не обязательное требование.

### 3. Трассировка (correlationId)

Без OpenTelemetry. Распределённая трассировка реализуется через сквозной `correlationId`:

1. **api-gateway** генерирует `correlationId` для каждого входящего запроса
2. **correlationId** передаётся в заголовке `X-Correlation-Id` всем сервисам
3. Сервисы **пробрасывают** `correlationId` в события (поле `correlationId`)
4. Все логи одной операции имеют одинаковый `correlationId`

Для отладки цепочки: `grep <correlationId> docker-compose-logs.txt`.

### 4. Healthcheck

Каждый сервис экспонирует:
```
GET /health → { "ok": true, "db": true, "nats": true, "uptime": 123456 }
```

### Итого: что добавляем в каждый сервис

| Компонент | Библиотека | Endpoint | Обязательно? |
|-----------|-----------|----------|-------------|
| Структурированные логи | pino | stdout | ✅ да |
| Метрики | prom-client | `GET /metrics` | ✅ да |
| Health | — | `GET /health` | ✅ да |
| Grafana | grafana/grafana | :3000 | ❌ опционально |
| Prometheus | prom/prometheus | :9090 | ❌ опционально |

## Последствия

### Положительные
- Можно отладить любой сбой по `correlationId`
- Метрики позволяют заметить деградацию (Ollama тормозит, БД перегружена)
- Healthcheck — основа для docker-compose health-зависимостей

### Отрицательные
- Дополнительный код в каждом сервисе (можно вынести в `@pmos/shared`)
- Prometheus + Grafana — ещё два контейнера (но опциональные)
- `pino` быстрее `console.log`, но не бесплатно

## Связанные ADR
- ADR-003: Event-Driven Communication (correlationId в событиях)
- ADR-001: API Gateway (генерация correlationId на входе)
