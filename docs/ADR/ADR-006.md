# ADR-006: Стратегия миграции данных (ETL из монолита)

## Статус
Accepted

## Контекст
Существующий монолит содержит 22 таблицы с данными, которые нужно перенести в новую архитектуру
(16 схем, event-driven сервисы). Проблемы:
- В монолите одна база `personalos`, таблицы с FK через все домены
- В новой архитектуре — схемы на сервис, без FK между схемами
- Часть данных (duplicated IDs) использует serial/autoincrement, а не UUID
- Нужна идемпотентная миграция, чтобы можно было перезапускать при ошибках

## Решение

### Стратегия: Event Bridge + Shadow Read

#### Фаза 1: Event Bridge (во время parallel run)
В старом монолите добавляем слой, который при каждом изменении данных публикует событие в NATS.
Новые сервисы читают эти события и строят свои read model'и.

```typescript
// В старом монолите — after каждого INSERT/UPDATE/DELETE
async function emitEvent(event: Event): Promise<void> {
  // Публикуем в NATS (если доступен)
  try {
    await natsConnection.publish(event.type, event);
  } catch {
    // NATS недоступен — не фатально, данные уже сохранены в монолите
    logger.warn({ eventType: event.type }, 'NATS unavailable, event lost');
  }
}
```

**Проблема**: NATS может быть недоступен во время миграции. Решение — двухфазный подход:
1. Публикуем через NATS (быстро)
2. При ошибке NATS — ничего не делаем (данные уже в монолите, догоним при ETL)

#### Фаза 2: ETL (полная выгрузка)
Перед cutover запускаем скрипт, который:
1. Читает все таблицы из старой БД
2. Трансформирует ID (serial → UUID, сохраняя legacy_id)
3. Публикует события в NATS для каждого типа сущности
4. Новые сервисы обрабатывают события, строят свои схемы

### Обработка ID

```sql
-- В каждой новой схеме
CREATE TABLE notes_.notes (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    legacy_id INTEGER,           -- старый ID из монолита (nullable)
    title TEXT NOT NULL,
    body_md TEXT NOT NULL,
    -- ...
);
```

**Правила**:
- Все entity в новой системе имеют UUID
- Старый ID сохраняется в поле `legacy_id` для обратной совместимости
- Ссылки на другие entity — по UUID, не по legacy_id

### Идемпотентность

Каждое событие проверяется по `event.id` перед обработкой:

```typescript
async function handleNoteCreated(event: NoteCreatedEvent): Promise<void> {
  // Проверяем, не обработано ли уже это событие
  const processed = await db.query(
    'SELECT 1 FROM search_rag_.processed_events WHERE event_id = $1',
    [event.id]
  );
  if (processed) return; // уже обработано

  // Обрабатываем
  await computeEmbeddingAndStore(event.data);

  // Отмечаем как обработанное
  await db.query(
    'INSERT INTO search_rag_.processed_events (event_id, processed_at) VALUES ($1, NOW())',
    [event.id]
  );
}
```

**Таблица `processed_events`** — в каждой схеме, для идемпотентной обработки событий.

### Зависимости миграции

Порядок выгрузки важен из-за ссылок:
1. **profiles** — ни от кого не зависит
2. **settings** — ни от кого не зависит
3. **notes** — зависит от profiles (profile_ids), но FK нет
4. **tasks** — зависит от profiles
5. **meetings** — зависит от profiles, projects
6. **projects** — зависит от profiles
7. **file_meta** — зависит от profiles
8. **Остальные** — по мере готовности зависимостей

### Проверка целостности

После миграции запустить скрипт валидации:
```sql
-- Проверяем что количество записей совпадает
SELECT count(*) FROM personalos.public.notes;
SELECT count(*) FROM notes_.notes;
-- Должны совпадать
```

**Критерий успеха миграции**:
- Все записи из монолита присутствуют в новых схемах
- Все UUID имеют корректные legacy_id
- Количество событий в NATS = количеству сущностей

### Откат

При проблемах:
1. Остановить новые сервисы
2. Переключить api-gateway обратно на старый монолит
3. Починить ETL, перезапустить (идемпотентность не даст дублей)

## Последствия

### Положительные
- Возможность мигрировать с остановкой на минуты, а не дни
- Идемпотентность позволяет перезапускать ETL без дублей
- legacy_id сохраняет обратную совместимость

### Отрицательные
- Дополнительная таблица `processed_events` в каждой схеме
- Нужно синхронизировать старые и новые ID при cutover
- Event bridge удваивает нагрузку на NATS во время parallel run
